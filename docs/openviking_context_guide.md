# 🗺 Руководство по иерархическому контексту L0 / L1 / L2 (OpenViking Pattern)

> **Назначение:** Простое и понятное объяснение трехуровневой модели организации контекста для AI-ассистентов. Данный паттерн позволяет сократить расход токенов на 40–80%, ускорить генерацию в 3–7 раз и полностью устранить галлюцинации моделей при работе с большими проектами. Документ оформлен как готовый рецепт для переноса в любые ваши проекты (backend, frontend, DevOps, монорепозитории).

---

## 💡 1. Главная проблема: почему «скормить все файлы» — плохая идея

Когда проект растет, разработчики часто пытаются решить вопрос контекста «в лоб»:
1. Заставляют ИИ рекурсивно читать десятки файлов или директорий.
2. Либо запихивают в системный промпт огромную документацию на тысячи строк.

**К чему это приводит на практике:**
* **Эффект «Lost in the Middle»:** Чем больше текст на входе, тем хуже нейросеть удерживает внимание на деталях и чаще галлюцинирует.
* **Перегрузка контекстного окна (OOM):** Локальные модели (14B) имеют комфортное окно в 16k–32k токенов. Несколько сырых файлов конфигурации или логов мгновенно забивают память и замедляют вывод.
* **Дороговизна и задержки:** Время первого токена (Time-To-First-Token) на сырых файлах увеличивается в разы (секунды ожидания вместо миллисекунд).

## 🎯 2. Идея OpenViking: Принцип «Google Maps» (Zoom-in)

Вместо того чтобы сразу загружать спутниковый снимок каждого кирпича на планете, карты показывают сначала континент, затем город, и только по клику — конкретный дом.

Паттерн делит знания проекта на **3 четких уровня детализации**:

```
 ┌─────────────────────────────────────────────────────────────┐
 │ L0: Глобальная карта (Abstract)                             │
 │ ~150 - 250 токенов | Понимание всего проекта за 0.1 сек     │
 └──────────────────────────────┬──────────────────────────────┘
                                │  Zoom-in (по запросу)
                                ▼
 ┌─────────────────────────────────────────────────────────────┐
 │ L1: Карточки подсистем (Subsystems / Contracts)             │
 │ ~300 - 500 токенов | Архитектура конкретного модуля          │
 └──────────────────────────────┬──────────────────────────────┘
                                │  Zoom-in (по запросу)
                                ▼
 ┌─────────────────────────────────────────────────────────────┐
 │ L2: Точные спецификации и CLI (Deep Reference & Code)       │
 │ По необходимости | Флаги утилит, схемы БД, сырые куски кода │
 └─────────────────────────────────────────────────────────────┘
```

## 🔍 3. Анатомия каждого уровня

### 🌐 Уровень L0: «Глобус» (Abstract Mental Map)
* **Размер:** ~150–250 токенов.
* **Формат:** Компактный JSON или короткий Markdown (`L0_index.json`).
* **Что содержит:**
  1. Одно предложение о назначении проекта.
  2. Список модулей/подсистем с кратким однострочным описанием и тегами.
  3. 3–5 ключевых «железных» правил проекта (Single Source of Truth, запрещенные действия).
* **Когда используется:** ИИ читает его **первым делом** при старте диалога или когда задача не привязана к конкретному файлу.
* **Пример из нашего dotfiles:**
  ```json
  {
    "project": "dotfiles",
    "subsystems": [
      { "id": "wm_niri", "name": "Niri Wayland", "summary": "Оконный менеджер и хоткеи" },
      { "id": "ai_stack", "name": "AI Stack", "summary": "Ollama, Khoj, Headroom, AnythingLLM" }
    ],
    "core_rules": [
      "Пакеты ставить строго через playbooks/vars/packages.yml",
      "Скрипты класть только в zsh/.zsh/scripts/"
    ]
  }
  ```

---

### 🏛 Уровень L1: «Район города» (Subsystem Architecture)
* **Размер:** ~300–600 токенов на подсистему.
* **Формат:** Отдельный Markdown-файл на каждый логический модуль (`subsystems/<id>.md`).
* **Что содержит:**
  1. Ответственность модуля (за что отвечает, за что НЕ отвечает).
  2. Точки входа и ключевые файлы конфигурации/кода.
  3. Архитектурные контракты (порты, форматы данных, зависимости от других модулей).
  4. Как тестировать изменения в этом модуле без перезапуска всей системы.
* **Когда используется:** Когда ИИ понял из L0, к какому модулю относится задача пользователя, он запрашивает **только эту L1-карточку**.
* **Результат:** 80% экономии контекста по сравнению с чтением всех исходников модуля.

---

### 🔬 Уровень L2: «Конкретный дом» (Deep Reference & Tools)
* **Размер:** Загружается точечно под конкретную операцию.
* **Формат:** Файлы справок CLI (`cli/<tool>.md`), схемы таблиц БД, журнал принятых решений (`adr/<id>.md`).
* **Что содержит:**
  1. Точные флаги утилит (`stow --help`, `niri msg --help`).
  2. Сигнатуры API или форматы DTO.
  3. Исторический контекст («Почему мы отказались от библиотеки X в пользу Y»).
* **Когда используется:** Только когда модели требуется точный синтаксис команды или обоснование сложного решения.
* **Результат:** Модель больше не «угадывает» флаги CLI и не выдумывает несуществующие параметры.

## 🔄 4. Как это работает в диалоге (Сценарий из жизни)

**Ситуация:** Пользователь пишет: *«Добавь горячую клавишу для открытия калькулятора в окнах»*.

1. **Без L0/L1/L2 (Старый подход):**
   * ИИ делает `find`, находит 15 файлов в `niri/`, читает их все (~2500 токенов).
   * Долго «думает», путается в синтаксисе KDL, тратит ваше время и память GPU.
2. **С трехуровневым контекстом:**
   * **Шаг 1:** ИИ видит L0: понимает, что за горячие клавиши отвечает модуль `wm_niri`.
   * **Шаг 2:** ИИ вызывает `project_knowledge(level="L1", target="wm_niri")` (тратит всего 400 токенов вместо 2500).
   * **Шаг 3:** Из L1 сразу видит: правила лежат в `cfg/keybinds.kdl`, формат KDL, а тестировать нужно через `niri msg action reload-config`.
   * **Результат:** Мгновенный, точный ответ без лишних итераций.

## 🛠 5. Как перенести этот паттерн в любой другой ваш проект

Чтобы внедрить эту систему в новый проект (например, Backend на Go/Rust или Web-приложение), достаточно создать простую структуру папок:

```
my-project/
├── .agents/
│   └── knowledge/
│       ├── L0_index.json              # 1. Общая карта проекта
│       ├── subsystems/                # 2. Карточки модулей (L1)
│       │   ├── auth_service.md
│       │   ├── database_schema.md
│       │   └── frontend_ui.md
│       ├── cli/                       # 3. Синтаксис внутренних CLI/скриптов (L2)
│       │   └── migrations.md
│       └── adr/                       # 4. Архитектурные решения (ADR)
│           └── 0001_use_postgresql.md
```

### Шаблон `L0_index.json` для любого проекта:
```json
{
  "project": "my-cool-service",
  "description": "REST API сервис обработки заказов на Go + PostgreSQL",
  "root_path": "/path/to/project",
  "updated_at": "2026-09-12",
  "subsystems": [
    {
      "id": "auth",
      "name": "Authentication & JWT",
      "summary": "Авторизация пользователей, генерация токенов, middleware",
      "l1_path": "subsystems/auth.md",
      "tags": ["jwt", "security", "middleware"]
    },
    {
      "id": "orders",
      "name": "Order Processing",
      "summary": "Бизнес-логика создания и оплаты заказов, интеграция со Stripe",
      "l1_path": "subsystems/orders.md",
      "tags": ["orders", "payments", "stripe"]
    }
  ],
  "core_rules": [
    "Все миграции БД создаются через `make migrate-new`",
    "Бизнес-логика не должна напрямую импортировать SQL-драйверы (только через интерфейс репозитория)"
  ]
}
```

### Шаблон карточки подсистемы `subsystems/<name>.md` (L1):
```markdown
# Подсистема: Order Processing (L1)

## Зона ответственности
Создание, валидация и проведение оплаты заказов.

## Ключевые файлы
- `internal/orders/service.go`: Бизнес-логика
- `internal/orders/repository.go`: Запросы к БД
- `internal/orders/handlers.go`: HTTP endpoints

## Контракты и зависимости
- База данных: таблицы `orders`, `order_items`
- Внешние API: Stripe Webhooks (`/api/v1/webhooks/stripe`)

## Как запускать и тестировать
- Запуск тестов модуля: `go test ./internal/orders/...`
```

## 🤖 6. Как поддерживать актуальность без ручной рутины

Главный страх разработчика: *«Документация устареет через неделю»*.
В нашем репозитории мы решили эту проблему комбинацией двух простых шагов:

1. **Детерминированный сканер (TypeScript/Python/Bash):**
   Скрипт проверяет реальную файловую структуру (список пакетов/директорий) и обновляет `L0_index.json`. Ошибки и галлюцинации здесь исключены на 100%.
2. **Локальная LLM (Ollama) по Git Diff:**
   Команда `mise run knowledge:sync`:
   * Берет `git diff` измененных файлов конкретного модуля.
   * Скармливает дифф локальной модели (`qwen2.5-coder:14b`).
   * Модель сама дописывает новые параметры или хоткеи в нужный `subsystems/*.md`.

## 📊 Резюме преимуществ

| Критерий | Без иерархии (Сырой поиск по файлам) | С иерархией L0 / L1 / L2 |
|---|---|---|
| **Расход токенов** | 2000–5000 токенов на простой вопрос | 200–500 токенов (-80%) |
| **Время отклика** | 1–3 секунды на чтение контекста | 100–300 мс (в 5 раз быстрее) |
| **Риск галлюцинаций** | Высокий (модель путает похожие файлы) | Минимальный (жесткие контракты L1) |
| **Устаревание** | Быстро забывается, где что лежит | Авто-синхронизация по `git diff` |
