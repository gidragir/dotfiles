## 🪲 Каталог выявленных багов и критических грабель

### 1. Синтаксис идентификатора провайдера: `generic-openai` vs `generic_openai`
* **Симптом:** При обращении к `@agent` вылетает ошибка:
  ```text
  Could not respond to message.
  No workspace agent provider set. Please set your agent provider in the workspace's settings
  ```
* **Причина:** В коде бэкенда (`server.js:1024`) в методе `AgentHandler.checkSetup()` проверка провайдера выполняется через `switch (this.provider)` с жесткой веткой:
  ```javascript
  case "generic-openai":
    if (!process.env.GENERIC_OPEN_AI_BASE_PATH) 
      throw new Error("API base path must be provided to use agents.");
    break;
  ```
  Использование snake_case (`generic_openai`) не матчится с веткой `generic-openai` и падает в `default`, вызывая ошибку «провайдер не задан».
* **Решение:** Везде (в таблице SQLite `workspaces.chatProvider`, `workspaces.agentProvider`, а также в `sync-prompts.ts`) использовать строго **`generic-openai`** (с дефисом).

### 2. Жизненный цикл движка Ollama: встроенный `llm serve` vs Standalone User Daemon
* **Проблема встроенного движка:**
  - AnythingLLM Desktop по умолчанию пытается запустить устаревший встроенный форк Ollama (`storage/engines/ollama/bin/llm serve` v0.20.7).
  - Встроенный форк не поддерживает современные флаги ускорения NVIDIA (Flash Attention, 8-битное квантование KV-кэша через переменные окружения), скачивает модели в `$HOME`, а при сбоях зависает и блокирует порт `11434`.
* **Целевое архитектурное решение (Standalone User Daemon):**
  - Развертывание независимой службы systemd пользователя: `~/.config/systemd/user/ollama.service` (управляется пакетом Stow `anythingllm` и плейбуком `playbooks/setup_ollama.yml`).
  - Служба запускает системный бинарник `/usr/bin/ollama serve` (пакет `ollama-cuda` в CachyOS/Arch) с аппаратным ускорением:
    ```ini
    [Service]
    ExecStart=/usr/bin/ollama serve
    Environment="OLLAMA_FLASH_ATTENTION=1"
    Environment="OLLAMA_KV_CACHE_TYPE=q8_0"
    Environment="OLLAMA_HOST=127.0.0.1:11434"
    Environment="OLLAMA_KEEP_ALIVE=30m"
    Environment="OLLAMA_MODELS=/data/models/ollama"
    ```
  - В `storage/.env` AnythingLLM глобально выставляется `LLM_PROVIDER='generic-openai'`. Это предотвращает запуск устаревшего встроенного процесса AnythingLLM и исключает конфликт портов.
  - Headroom проксирует вызовы с порта `8787` на постоянный порт `11434`.
  - Воркспейсы AnythingLLM подключаются через Headroom по протоколу `generic-openai`.

### 3. Настройка апстрима Headroom на локальный Ollama (`OPENAI_TARGET_API_URL`)
* **Симптом:** При обращении через порт 8787 возвращается:
  ```json
  {"error": {"message": "Missing bearer authentication in header"}}
  ```
  или
  ```json
  {"error": {"message": "Incorrect API key provided: dummy. You can find your API key at https://platform.openai.com..."}}
  ```
* **Причина:** По умолчанию Headroom перенаправляет запросы `/v1` в облако `api.openai.com`.
* **Решение:** При установке службы Headroom через `headroom install apply` обязательно передавать переменную целевого URL:
  ```bash
  headroom install apply \
      --scope user \
      --preset persistent-service \
      --backend anyllm \
      --anyllm-provider openai \
      --env OPENAI_TARGET_API_URL=http://127.0.0.1:11434/v1 \
      --env HEADROOM_PROTECT_TOOL_RESULTS="search_files,read_file,write_file,execute_command,git_status,git_diff" \
      --env HEADROOM_NO_CCR=1 \
      --env DATABASE_URL=postgresql://headroom:headroom_password@127.0.0.1:5432/headroom_cache \
      --protect-tool-results "search_files,read_file,write_file,execute_command,git_status,git_diff" \
      --code-aware \
      --port 8787
  ```
  Проверка: `curl -s -H "Authorization: Bearer headroom" http://127.0.0.1:8787/v1/models` должна сразу возвращать список моделей Ollama.

### 4. Вытеснение инструментов агента реранкером AnythingLLM (`IntelligentSkillSelector`)
* **Симптом:** Агент AnythingLLM не вызывает `headroom_compress` или нужные инструменты, хотя они зарегистрированы в `anythingllm_mcp_servers.json`.
* **Причина:** AnythingLLM запускает семантический реранкер (`ms-marco-MiniLM-L-6-v2`), который из всех зарегистрированных инструментов отбирает **только топ-15** наиболее похожих на текст пользовательского промпта. Если активны дубликаты (например, встроенный плагин `filesystem-agent` + внешний `@modelcontextprotocol/server-filesystem` MCP сервер + дубликаты алиасов `host-cli`), общее число инструментов достигает 36, и реранкер выкидывает `headroom_compress` из активного контекста.
* **Решение:**
  - Отключать дублирующие плагины в `system_settings` таблицы SQLite (`sync-prompts.ts`):
    ```typescript
    {
      label: "disabled_agent_skills",
      value: JSON.stringify(["filesystem-agent", "web-scraping", "document-summarizer"]),
    }
    ```
  - В `bash-mcp-server.mjs` убирать дублирующие алиасы (оставлять только уникальные инструменты: `execute_command`, `git_status`, `git_diff`).
  - **Увеличение лимита реранкера через `.env` (Критически важно):** В коде класса `IntelligentSkillSelector` AnythingLLM заложена поддержка переменных окружения:
    ```bash
    # В ~/.config/anythingllm-desktop/storage/.env
    AGENT_SKILL_RERANKER_TOP_N='30'       # Расширяет выборку с дефолтных 15 до 30 инструментов
    AGENT_SKILL_RERANKER_ENABLED='true'   # Либо 'false' для полной отмены фильтрации
    ```
  - В `bash-mcp-server.mjs` убирать дублирующие алиасы (оставлять только уникальные инструменты: `execute_command`, `git_status`, `git_diff`).
  - Отключать нерелевантные плагины (включая `rag-memory`, если работа ведется с локальными файлами на диске).

### 5. Холодный старт и чтение `.env` процессом AnythingLLM
* **Симптом:** Переменные добавлены в `~/.config/anythingllm-desktop/storage/.env`, но бэкенд их не видит.
* **Причина:** Пакет `dotenv` парсит файл `.env` ровно один раз при инициализации Node.js процесса бэкенда Electron.
* **Решение:** Любые правки переменных окружения в `.env` требуют полного перезапуска Electron-приложения (закрыть окно и запустить заново через `Mod+A`).

### 6. Инициализация глобальных правил в Antigravity IDE
* **Симптом:** Новое правило `~/.gemini/config/rules/headroom.md` не применяется в текущем открытом чате.
* **Причина:** Antigravity считывает глобальные правила и локальные файлы `AGENTS.md` только в момент старта диалоговой сессии (компиляция системного промпта).
* **Решение:** Добавленные через Stow правила вступают в силу со следующего созданного диалога/сессии.

### 7. Поведение команды `@agent` в окне чата AnythingLLM
* **Симптом:** Пользователь пишет в обычный чат `@agent изучи в моем obsidian...`, AnythingLLM отвечает `@agent: Swapping over to agent chat. Type /exit to exit agent execution loop...`, но саму инструкцию игнорирует.
* **Причина:** В интерфейсе AnythingLLM префикс `@agent` обрабатывается как переключатель режима (mode toggle command). Он переводит сессию в цикл агента, а полезная нагрузка (сообщение, идущее после `@agent`) в момент переключения не передается в агентную петлю.
* **Решение:** 
  1. Первое сообщение `@agent` переводит чат в режим агента.
  2. Запрос или инструкцию по анализу заметок необходимо отправлять **следующим сообщением** уже внутри активного агентного режима.

### 8. Инъекция инструментов памяти Headroom (`memory_search`) и зависание стриминга
* **Симптом:**
  1. Агент при поиске по файлам всегда вызывает `memory_search({"query":"..."})` вместо `search_files`.
  2. Получив пустой результат из памяти, модель галлюцинирует общие рассуждения из pre-training датасета.
  3. На следующем запросе генерация намертво зависает (бесконечный спиннер, модель не отвечает).
* **Причина:**
  1. Демон Headroom был развернут с флагом `--memory` (`HEADROOM_MEMORY_ENABLED=1`).
  2. При включенном модуле памяти Headroom Proxy **автоматически инжектирует** в запрос к LLM свои собственные инструменты (`memory_search`, `memory_save`, `memory_update`, `memory_delete`).
  3. Headroom принудительно дописывает в системный промпт инструкцию:
     `- ALWAYS call memory_search BEFORE searching files`.
  4. Компактная модель (Gemma 4B) строго следует этой инструкции, вызывает `memory_search`, но база памяти Headroom пуста (так как файлы лежат на диске).
  5. В режиме SSE-стриминга перехватчик `streaming.py` в Headroom при повторных обращениях в одной агентной петле теряет синхронизацию tool-call состояния с бэкендом AnythingLLM, что приводит к дедлоку и зависанию ответа.
* **Решение:**
  - Отключить модуль памяти в Headroom: развертывать сервис строго без флага `--memory` (`HEADROOM_MEMORY_ENABLED=0` в `manifest.json` и `run-headroom.sh`).
  - Headroom должен использоваться исключительно для своей ключевой задачи: сжатия контекста (CCR), дедупликации и кэширования без вмешательства в инструменты и промпты.

### 9. Оптимизация поиска файлов для локальных SLM: `search_files` vs `server-filesystem` vs `grep -rn`
* **Симптом:**
  1. Модель находит только 1-2 файла из обширного набора релевантных заметок (например, видит один файл со строгим вхождением слова и пропускает остальные заметки по той же теме).
  2. Ассистент в воркспейсе программирования (`assistant-chats`) не может искать файлы в репозиториях (`/data/projects`).
* **Причины:**
  1. **Морфология и падежные окончания:** Прямой поиск по подстроке (`rg -i -l 'слово'`) чувствителен к падежам и словоформам. Если в запросе передано существительное в одной форме, поиск пропускает документы, где используются другие падежи, формы множественного числа или производные части речи в заголовках.
  2. **Поиск без учета путей каталогов:** По умолчанию утилита `fd` сопоставляет шаблон только с базовым именем файла (basename). Если релевантные документы сгруппированы внутри тематической папки, но их собственные имена файлов не дублируют название этой папки, поиск без флага `--full-path` (`-p`) их не находит.
  3. **Ограничение построчного grep:** Вызов `grep -rn ... | head -n 50` возвращает строки текста. Если в одном файле много совпадений, вывод забивается строками одного документа, отсекая остальные файлы.
  4. **Перегрузка инструментами:** Официальный MCP `@modelcontextprotocol/server-filesystem` регистрирует 22+ инструмента со сложными схемами, вызывая у компактных моделей (Gemma 4B) распыление внимания и ошибки валидации.
* **Решение:**
  - В `bash-mcp-server.mjs` реализован умный легковесный инструмент `search_files`:
    - Функция `extractSearchPatterns`: парсит поисковую фразу, отсекает стоп-слова, выделяет основы слов (стемминг падежных флексий), формируя мульти-паттерн regex (`stem1|stem2`).
    - Вызов `fd -i -p -t f` выполняет регистронезависимый поиск с флагом `--full-path`, находя файлы как по именам, так и по родительским каталогам.
    - Вызов `rg -i -l --max-count=1` находит документы по содержимому с учетом выделенных стеммов.
    - Поддерживается параметр `directory` (любой путь: кодовая база, документы или репозитории).
    - Результаты дедуплицируются (`sort -u | head -n 35`), выдавая компактный список файлов для точечного чтения через `read_file`.

### 10. Разделение трафика Headroom: AnythingLLM vs Antigravity IDE
* **Почему в диалоге с Antigravity Headroom не виден по умолчанию:**
  - **Antigravity IDE:** Работает напрямую с облачными моделями Google Gemini через внутренний API IDE. Трафик не идет через локальный HTTP-прокси `127.0.0.1:8787`. Headroom подключен к Antigravity как MCP-сервер (`headroom_stats`, `headroom_compress`, `headroom_retrieve`), который вызывается при необходимости или по запросу пользователя.
  - **AnythingLLM (Ollama):** Полностью завернут на `http://127.0.0.1:8787/v1` (провайдер `generic-openai`). Весь входящий контекст локальной модели Gemma 4B сжимается через Headroom (актуальная статистика доступна через команду `headroom savings` или MCP `headroom_stats`).

### 11. Галлюцинация несуществующих заметок при падении MCP-сервера и симуляция вызова инструментов
* **Симптом:**
  1. В режиме `@agent` модель выводит текст, имитирующий системный вызов инструмента:
     ```text
     *(Activating search functionality across /data/obsidian/ZETA/, /data/obsidian/PARA/, и /data/obsidian/MOC/)*
     *... (Simulation of file search executing) ...*
     [System Message: Search executed.]
     ```
  2. Модель выдает список полностью вымышленных заметок (например, `[[Лидерство как сервис]]`, `[[MOC: Развитие личного бренда]]`, `[[Характеристики харизматичного лидера]]`), которых никогда не было в хранилище Obsidian.
  3. В предыдущих сессиях поиск находил только один файл `2. Strategic.md` и игнорировал реальные заметки (`Как быть лидером.md`, `Почему мне хочется быть лидером.md`, `Что меня мотивирует быть лидером.md`, `Мое состояние лидера.md`).
* **Причины:**
  1. **Синтаксическая ошибка в MCP-сервере (`SyntaxError: Unexpected token ']'`):** В файле `bash-mcp-server.mjs` при редактировании были нарушены фигурные скобки. На старте бэкенда Electron процесс `node bash-mcp-server.mjs` аварийно падал:
     ```text
     [MCPHypervisor] Failed to start MCP server: host-cli {"error":"MCP error -32000: Connection closed"}
     ```
     В результате MCP-сервер `host-cli` не зарегистрировал ни одного инструмента в кластере агента AnythingLLM.
  2. **Поведение локальной SLM (Gemma 4B) без инструментов:** В системном промпте воркспейса (`onlychats.md`) модели прямо предписано использовать инструменты `search_files` и `read_file` для работы с Obsidian. Когда модель получает инструкцию использовать инструмент, которого нет в переданной схеме инструментов, компактная локальная модель начинает «отыгрывать роль» (roleplay/simulation) и генерировать текстовые артефакты выполнения поиска, придумывая правдоподобные названия заметок из своего датасета обучения.
  3. **Падежные флексии русского языка (почему ранее находился только один файл):** Предыдущая наивная реализация поиска искала подстроку строго по введенному слову (`лидерство`). Файлы пользователя были озаглавлены в творительном и родительном падежах (`...лидером.md`, `...лидера.md`). Поиск по `лидерство` их отсекал, находя только файл `2. Strategic.md`, внутри которого встретилось точное слово «лидерство».
* **Решение:**
  - В `bash-mcp-server.mjs` развернут полноценный MCP-сервер с инструментами:
    - `search_files`: Полноценный стемминг русского (отсечение суффиксов `-ство`, `-ость`, падежных окончаний `-ом`, `-ами`, `-ей`, `-ах` и т.д.) и английского языков (`-ship`, `-ing`, `-ed`, `-tion`). Многоуровневый скоринг: совпадение по имени файла (+10), по пути (+5), по содержимому через `rg` (+2), умножение на количество совпавших стеммов. Дополнительный бонус (+5) для `.md` файлов и извлечение сниппета первого заголовка/строки.
    - `read_file`: Безопасное чтение файла с защитой контекстного окна (`max_lines`, `offset`).
    - `write_file`: Создание или дописывание (`append: true`) в заметки.
    - `execute_command`, `git_status`, `git_diff`: Системные команды.
  - Проверена работа через JSON-RPC Stdio: вызов `search_files` по запросу о лидерстве мгновенно возвращает все реальные заметки (`Развитие лидерства.md`, `Как быть лидером.md`, `Почему мне хочется быть лидером.md`, `Что меня мотивирует быть лидером.md`, `Мое состояние лидера.md`, `2. Strategic.md` и т.д.).

### 12. Подмена результатов MCP-инструментов маркерами CCR (`<<ccr:...>>`) в Headroom Proxy
* **Симптом:**
  1. Модель в чате AnythingLLM после выполнения MCP-инструмента выводит сырой системный маркер Headroom, например:
     ```text
     Заголовок (или путь): <<ccr:c59e98af6e7f,string,8.0KB>>
     ```
  2. Модель теряет способность анализировать выданные файлы, заявляя, что файл пуст или имеет странный заголовок `<<ccr:...>>`.
* **Причина:**
  - По умолчанию Headroom Proxy работает в режиме агрессивного сжатия контекста (CCR — *Content-Centric Reduction*). Когда инструмент MCP возвращает объемные данные (например, результат поиска по хранилищу размером ~8 KB), прокси заменяет этот блок текста на компактную ссылку-заглушку `<<ccr:хеш,тип,размер>>`, сохраняя исходный текст в своей внутренней KV-базе.
  - Большие облачные модели с глубоким контекстом и плагинами Headroom умеют восстанавливать такие чанки через динамический tool recall (`headroom_retrieve`).
  - Компактные локальные SLM (Gemma 4B, Qwen 4B) не знают внутренний протокол CCR. Они воспринимают строку `<<ccr:...>>` буквально как заголовок заметки или путь к файлу и выводят её пользователю, теряя весь смысл запроса.
* **Решение (Архитектурный паттерн Путь А):**
  1. **Исключение критических инструментов из сжатия:**
     В параметры запуска `headroom proxy` передается флаг `--protect-tool-results`:
     ```bash
     --protect-tool-results search_files,read_file,write_file,host-cli-search_files,host-cli-read_file,host-cli-write_file,execute_command
     ```
     (или переменная окружения `HEADROOM_PROTECT_TOOL_RESULTS`).
  2. **Отключение генерации плейсхолдеров CCR:**
     Флаг `--no-ccr` (или `HEADROOM_NO_CCR=1`) гарантирует, что даже если какие-то данные оптимизируются, они никогда не будут заменяться на строковые маркеры `<<ccr:...>>` в теле диалога.
  3. **Фиксация в манифесте службы `systemd`:**
     В файле `~/.headroom/deploy/default/manifest.json`:
     ```json
     {
       "base_env": {
         "HEADROOM_PROTECT_TOOL_RESULTS": "search_files,read_file,write_file,host-cli-search_files,host-cli-read_file,host-cli-write_file,execute_command",
         "HEADROOM_NO_CCR": "1"
       },
       "proxy_args": [
         "--protect-tool-results",
         "search_files,read_file,write_file,host-cli-search_files,host-cli-read_file,host-cli-write_file,execute_command",
         "--no-ccr"
       ]
     }
     ```
     После чего выполняется перезапуск: `systemctl --user restart headroom-default.service`.
  4. **Контроль размера вывода на уровне самого MCP-сервера:**
     Чтобы контекстное окно 8K/16K локальной модели не переполнялось сырым текстом, MCP-сервер `bash-mcp-server.mjs` не отдает файлы целиком, а возвращает структурированный список с очищенными первыми 220 символами каждого документа (краткое содержание без frontmatter) и жестким лимитом (`max_results = 25`). Общий размер ответа остается в пределах 2–4 KB, что идеально для Gemma 4B.

### 13. Двухконтурная архитектура Headroom: Cloud Antigravity (MCP) vs Local AnythingLLM (Proxy & Cache)
* **Проблема восприятия:** «Если мы отключили сжатие результатов инструментов в прокси, не теряется ли вообще смысл Headroom?»
* **Ответ и архитектурное разделение:**
  Смысл Headroom не только не теряется, но раскрывается в двух специализированных контурах:
  ```
  ┌──────────────────────────────────────────────────────────────────────────────────┐
  │                           КОНТУР 1: Antigravity IDE                              │
  │  • Трафик: Cloud Gemini API (напрямую через gRPC/HTTPS, минуя локальный порт).  │
  │  • Роль Headroom: Автономный MCP-сервер (~/.gemini/config/mcp_config.json).      │
  │  • Инструменты: headroom_stats, headroom_compress, headroom_retrieve.            │
  │  • Задачи: Анализ эффективности сессий, компрессия больших артефактов и логов.   │
  └──────────────────────────────────────────────────────────────────────────────────┘

  ┌──────────────────────────────────────────────────────────────────────────────────┐
  │                         КОНТУР 2: AnythingLLM + Ollama                           │
  │  • Трафик: 100% локальный инференс через Reverse Proxy (Generic OpenAI :8787).   │
  │  • Роль Headroom: HTTP Reverse Proxy перед локальным Ollama (:11434).            │
  │  • Задачи:                                                                       │
  │    1. Кэширование системных префиксов (Prefix-frozen cache).                    │
  │    2. Дедупликация идентичных запросов и истории чата в диалоговом окне.         │
  │    3. Предотвращение деградации VRAM и ускорение генерации повторных ответов.    │
  │    4. Полный учет экономии токенов и стоимости (headroom savings).               │
  └──────────────────────────────────────────────────────────────────────────────────┘
  ```
  Отключение подмены на `<<ccr:...>>` для вывода `search_files` убирает сбой синтаксиса у компактных моделей, но сохраняет кэширование диалога, системного промпта и контекста сессии.

### 14. Архитектура и алгоритмы `bash-mcp-server.mjs`
* **Почему специализированный сервер лучше официального `@modelcontextprotocol/server-filesystem`:**
  - Официальный сервер регистрирует более 20 громоздких инструментов с глубокими JSON-схемами (`list_directory`, `get_file_info`, `move_file`, `search_files`, `directory_tree` и т.д.).
  - Для SLM с параметрами 4B это создает когнитивную перегрузку («распыление внимания» на валидацию схем) и частые ошибки генерации JSON (`tool_call validation error`).
  - `bash-mcp-server.mjs` предоставляет только 6 точечных, отказоустойчивых инструментов:
    1. `search_files`: морфологический поиск по Obsidian или проектам.
    2. `read_file`: постраничное безопасное чтение.
    3. `write_file`: атомарная запись или дописывание (`append: true`).
    4. `execute_command`: выполнение CLI-утилит хоста в изолированной среде.
    5. `git_status`: быстрый снимок состояния Git.
    6. `git_diff`: построчный диф изменений.
* **Алгоритм морфологического поиска (`searchFilesHandler`):**
  1. **Очистка и стемминг:**
     - Регулярные выражения удаляют пунктуацию, оставляя значимые слова длинее 2 символов.
     - Русский стеммер удаляет окончания падежей, множественного числа и суффиксы:
       `/(иями|ыями|ями|ами|ей|ов|ев|ам|ям|ах|ях|ою|ею|ую|юю|ия|ья|ие|ье|ое|ее|ому|ему|ых|их|ую|ю|а|я|о|е|ы|и|у|ю|ь|ство|ость|ение|ание)$/i`
       *(например, `лидерство` $\to$ `лидер`, `лидером` $\to$ `лидер`, `лидерский` $\to$ `лидер`)*.
     - Английский стеммер нормализует формы:
       `/(sses|ies|ing|ed|ly|ness|ship|tion|ment|able|ible|ful|less|est|er|s)$/i`.
  2. **Многоуровневый скоринг релевантности:**
     - Совпадение стемма в имени файла (basename): **+10 очков**.
     - Совпадение стемма в пути файла (директории): **+5 очков**.
     - Совпадение в содержимом файла (через быстрый `rg -i`): **+2 очка**.
     - Документ формата Markdown (`.md`): бонус **+5 очков**.
     - Общий балл умножается на долю совпавших стеммов запроса (`matchedStems / totalStems`).
  3. **Очистка Markdown Frontmatter и генерация сниппета:**
     - При формировании выдержки отсекается YAML frontmatter:
       `content.replace(/^---\n[\s\S]*?\n---\n*/, "")`.
     - Извлекаются первые 220 значимых символов заметки, давая модели контекст сути заметки без необходимости открывать файл целиком.
  4. **Формат ответа (Obsidian Wikilinks):**
     Результаты оборачиваются в синтаксис `[[Название Заметки]] (/абсолютный/путь)`, что заставляет LLM использовать эти же викиссылки в финальном ответе пользователю.

### 15. Предотвращение симуляции и галлюцинаций в системных промптах (`onlychats.md`)
* **Симптом:**
  Когда у модели нет прямого доступа к файлам или поиск ничего не вернул, модель начинает выдумывать гипотетические статьи: «Предположим, у вас есть заметка `[[Лидерство как сервис]]`...».
* **Решение в `prompts/onlychats.md`:**
  В системный промпт внедрен строгий контракт поведения:
  ```markdown
  - ⚠️ КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО:
    1. Имитировать или симулировать поиск текстовыми сообщениями вида "*(Simulation of search...)*" или "*(Activating search...)*".
    2. Придумывать несуществующие названия заметок или гипотетические статьи (например, "Лидерство как сервис", если такого файла не вернул инструмент).
    3. Если инструмент `search_files` вернул список заметок, ты ОБЯЗАН использовать ТОЛЬКО названия и выдержки из этого списка.
    4. Все ссылки на найденные заметки оформляй в виде красивых Obsidian-викиссылок: `[[Имя заметки]]`.
  ```
  Это пресекает любые фантазии и направляет внимание модели исключительно на факты из базы знаний пользователя.

### 10. Оптимизация под RTX 4070 Ti Super (16 ГБ VRAM) и модели класса 14B
* **Обоснование отказа от 4B и 32B:**
  - Модели 4B недоиспользуют 16 ГБ VRAM (занимают ~3 ГБ, простаивает 13 ГБ), склонны к галлюцинациям и ошибкам в синтаксисе Tool Calling.
  - Модели 32B требуют 20–24 ГБ VRAM; сжатие в Q3_K_S резко роняет точность, а малейший контекст вызывает CPU offload и обрушивает генерацию до 3 т/с.
  - Модели класса **14B (Q4_K_M)** весят ~9 ГБ VRAM, оставляя 5–6 ГБ под рабочий контекст (8k–32k токенов) и выдавая 45–65 токенов/сек.
* **Распределение по воркспейсам:**
  - `assistant-chats` ➔ **`qwen2.5-coder:14b`** (DevOps, CachyOS, Ansible, Bash, Git atomic commits, MCP tool calls).
  - `onlychat` ➔ **`qwen2.5:14b`** (Obsidian vault `/data/obsidian`, синтез, философия, русскоязычная эрудиция).
  - `my-workspace` ➔ **`deepseek-r1:14b`** (Reasoning, многоэтапная логика, сложные алгоритмы и deep research).
* **Аппаратный стек ускорения (в `~/.config/systemd/user/ollama.service`):**
  - `OLLAMA_FLASH_ATTENTION=1`: снижает потребление VRAM на 30–40% под KV-кэш на архитектуре Ada Lovelace.
  - `OLLAMA_KV_CACHE_TYPE=q8_0`: сжимает кэш контекста вдвое без потери качества, позволяя держать контекст до 32k токенов.
  - `OLLAMA_MAX_LOADED_MODELS=1`: критический лимит для 16 ГБ VRAM, предотвращающий одновременное удержание в памяти двух 14B моделей ($9 + 9 = 18$ ГБ) при смене воркспейса (исключает CPU offload и деградацию до 3 т/с).
  - `OLLAMA_NUM_PARALLEL=1`: ограничивает параллельные слоты контекста для сохранения VRAM под длинные сессии одного пользователя.
  - `OLLAMA_MODELS=/data/models/ollama`: хранение весов на высокоскоростном NVMe Btrfs сжатом диске.

### 16. Динамическая привязка локальных RAG-документов по слагу воркспейса
* **Симптом:** После добавления папки `/data/obsidian` в базу через скрипт синхронизации, в воркспейсе `onlychat` документов нет, а они отображаются в дефолтном `my-workspace`.
* **Причина:** Хардкод `workspaceId: 1` в `sync-prompts.ts`. На чистой установке `my-workspace` имеет `id: 1`, а `onlychat` получает `id: 3`.
* **Решение:** Выполнять динамический запрос `SELECT id FROM workspaces WHERE slug = 'onlychat'` и привязывать `workspace_documents` и `document_sync_queues` строго к полученному ID.

### 17. Обязательное отключение встроенного плагина `filesystem-agent`
* **Проблема:** Если в `disabled_agent_skills` не указан `filesystem-agent`, AnythingLLM загружает свои встроенные инструменты работы с файлами, создавая дубли с MCP `bash-mcp-server`. Реранкер вытесняет `headroom_compress` и `atomic-commits`.
* **Решение:** В `sync-prompts.ts` передавать `disabled_agent_skills: ["filesystem-agent", "web-scraping", "document-summarizer", "rag-memory"]`.
